= Binary Quantization with RaBitQ
:page-topic-type: guide
:page-ui-name: {ui-name}
:page-product-name: {product-name}
:description: RaBitQ is a binary quantization method for reducing the storage and memory requirements of vector indexes.
:stem: 
:page-toclevels: 3

[abstract]
{description}

RaBitQ targets large-scale vector search workloads.
It prioritizes reduced memory overhead and faster candidate retrieval over the uncompressed accuracy of a full-precision (FP32) index.

At the default setting of `nbit=1`, RaBitQ can provide up to 32x compression compared with unquantized FP32 vectors.
The actual storage savings and search performance depend on vector dimensionality, dataset distribution, index configuration, and whether full-precision vectors are retained for rescoring.

[#prerequisites]
== Prerequisites

* *Index Types:* Supported only on Hyperscale Vector Indexes (HVI) and Composite Vector Indexes (CVI).
* *Vector Types:* Supported on dense vectors only.
Sparse vectors are not supported.

NOTE: RaBitQ is also available for Search Vector Indexes. For more information, see xref:vector-search:vector-search-index-architecture.adoc#ivf-binary[IVF Indexes and Binary Quantization].

[#quantization-comparison]
== Quantization Comparison (SQ, PQ, and RaBitQ)

[cols="1,2,2,2,2,2",options="header"]
|===
| Quantization | Compression & Storage | Recall & Accuracy | Index Build Time | Query Latency | When to Choose

| *SQ* (Scalar)
| Moderate compression (~4x vs. FP32).
| High recall; preserves vector distribution well.
| Fast and simple build process.
| Low latency for general queries.
| You need a balanced default with predictable behavior and high recall.

| *PQ* (Product)
| High compression (8x–64x depending on subvectors and bits).
| Variable recall depending on codebook training and dataset.
| Slower build; requires codebook training.
| Efficient search on memory-constrained datasets.
| You need maximum memory reduction on clustered datasets and can accept training overhead.

| *RaBitQ* (Binary)
| Maximum compression (~32x at `nbit=1` vs. FP32; decreases as `nbit` increases).
| Lower first-phase recall at `nbit=1`; two-phase rescoring restores high recall.
| Fast build time (at least 3 times faster than PQ)
| Fast candidate search; rescoring adds slight query overhead.
| You have large, high-dimensional datasets (384 dimensions or more) and prioritize low memory footprint and fast builds.
|===

NOTE: Compression, recall, build times, and query latency depend on dataset size, vector dimensionality, index configuration, and query workload.
Always benchmark with representative data before choosing a quantization method in production.

[#recommended-use-and-dimensionality]
== Recommended Use and Dimensionality

Binary quantization works best on high-dimensional vectors (384 dimensions or more), such as embeddings from transformer models (for example, 384, 768, or 1536 dimensions).

On these vectors, RaBitQ reduces memory by up to ~32x and speeds up distance calculations using bitwise distance.
Combined with rescoring, it has minimal impact on search quality.
For lower-dimensional datasets (< 384 dimensions), Scalar Quantization (SQ) or unquantized indexes usually give better recall and less sensitivity to quantization loss.

[#tuning]
=== Tuning the Number of Bits

The `nbit` setting in the `description` parameter controls the number of bits allocated per vector dimension during quantization. Supported values range from `1` to `9` (default: `1`).

[cols="10,15,20,25",options="header"]
|===
| `nbit` Value | Compression Ratio | Recall Profile | Recommended Use Case

| `1` (Default)
| Highest (~32x vs. FP32)
| Lowest first-phase recall; relies on Phase 2 rescoring
| Huge, high-dimensional datasets where memory footprint and candidate search speed are primary concerns.

| `2–4`
| Moderate (8x–16x vs. FP32)
| Balanced first-phase recall and compression
| General large-scale workloads requiring a balance of memory savings and coarse-search accuracy.

| `5–9`
| Lower (3.5x–6x vs. FP32)
| Higher first-phase recall
| Workloads prioritizing candidate accuracy over maximum compression.
|===

Higher `nbit` values improve candidate retrieval accuracy in Phase 1 at the expense of higher index memory and storage footprint.

[#training-data-reqs]
=== Training Data Requirements

Building a RaBitQ index requires sufficient sample data to train the IVF centroid clusters and quantization parameters:

* The target collection must contain at least 1,000 non-null vector documents before index creation begins.
* If index creation is attempted on an empty collection or a dataset with fewer than 1,000 non-null vectors, the index build fails and returns the error:
+
[source,text]
----
HYR0126: Insufficient training data to build index.
A minimum of 1000 non-null vectors is required.
----

Make sure your collection is populated with representative vector data before creating the index.

[#creating]
== Creating a Vector Index with RaBitQ

You can create a Hyperscale Vector Index (HVI) or Composite Vector Index (CVI) that uses Randomized Binary Quantization (RaBitQ) to achieve high compression for large vector datasets.

When creating a RaBitQ index, configure the `description` parameter with `RaBitQ` and an optional `nbit` suffix.
You can set the similarity metric to Cosine, L2, or Dot product.

Make sure your dataset meets the <<prerequisites>> and the <<training-data-reqs>>.

[#creating-examples]
=== Examples for Creating RaBitQ Indexes

.Hyperscale Vector Index (HVI) with RaBitQ
====
The following {sqlpp} statement creates a standalone Hyperscale Vector Index on a dense 768-dimensional vector field using RaBitQ with 1 bit per dimension (`nbit=1` default):

[source,sqlpp]
----
CREATE VECTOR INDEX `idx_hotel_desc_rabitq`
ON `travel-sample`.`inventory`.`hotel`(`description_vector` VECTOR)
USING GSI
WITH {
  "dimension": 768,
  "description": "IVF,RaBitQ",
  "similarity": "L2",
  "persist_full_vector": true
};
----
====

.Composite Vector Index (CVI) with RaBitQ
====
The following {sqlpp} statement creates a Composite Vector Index that combines a scalar filter field (`city`) with a quantized vector field using 4 bits per dimension (`RaBitQ4`):

[source,sqlpp]
----
CREATE VECTOR INDEX `idx_hotel_city_vector_rabitq`
ON `travel-sample`.`inventory`.`hotel`(`city`, `description_vector` VECTOR)
USING GSI
WITH {
  "dimension": 768,
  "description": "IVF,RaBitQ4",
  "similarity": "L2",
  "persist_full_vector": true
};
----
====

[#migrating]
== Migrating Existing Indexes to RaBitQ

You cannot convert an existing vector index (such as an unquantized, SQ8, or PQ index) to use RaBitQ in place.
Index creation defines quantization parameters, similarity metrics, and nbit values as immutable, and ALTER INDEX cannot modify them.

To migrate an existing production vector index to RaBitQ without application downtime, follow the create-and-swap workflow:

. Create a new RaBitQ index using a temporary name:
+
[source,sqlpp]
----
CREATE VECTOR INDEX `idx_items_vector_rabitq`
ON `catalog`.`products`.`items`(`embedding` VECTOR)
USING GSI
WITH {
  "dimension": 768,
  "description": "IVF,RaBitQ",
  "similarity": "L2",
  "persist_full_vector": true
};
----

. Monitor the build status until the index is fully online.
Check the build progress in the Couchbase Web Console or by querying `system:indexes`:
+
[source,sqlpp]
----
SELECT name, state, progress
FROM system:indexes
WHERE name = "idx_items_vector_rabitq";
----
+
Wait until `state` returns `"online"`.

. Switch query traffic to the new index.
Update application queries (if using explicit index hints (`USE INDEX`) or allow the {sqlpp} query optimizer to evaluate and route requests to the new RaBitQ index.

. Drop the old index once traffic has safely transitioned:
+
[source,sqlpp]
----
DROP INDEX `catalog`.`products`.`items`.`idx_items_vector_legacy`;
----

[#rescoring]
== Rescoring and Vector Retention Configuration

RaBitQ uses a two-phase search process:

. Phase 1 (Coarse Search): Fast candidate retrieval using bitwise distance across the quantized index.
. Phase 2 (Rescoring): Reranking of the retrieved candidate vectors against the original full-precision vectors, using the distance metric specified in the query (such as Cosine or Euclidean).

Because RaBitQ uses 1-bit or low-bit approximations during Phase 1, candidate filtering alone can produce lower recall than uncompressed FP32 search.
Couchbase recommends retaining full-precision vectors and enabling Phase 2 rescoring for production vector search workloads.

The `persist_full_vector` parameter in the `WITH` clause controls whether Couchbase stores full-precision (FP32) vectors alongside the quantized index to support Phase 2 rescoring:

[cols="1,1,3",options="header"]
|===
| Setting | Default | Behavior

| `persist_full_vector: true`
| Yes
| Retains original FP32 vectors on disk alongside the quantized index.
Enables automatic Phase 2 rescoring during queries to recover high recall while retaining the memory and speed benefits of binary quantization.

| `persist_full_vector: false`
| No
| Stores only the binary-quantized vectors.
Maximizes disk space savings and reduces index storage footprint, but disables Phase 2 rescoring.
Queries return candidates ranked solely by bitwise distance, which can result in lower recall.
|===

When `persist_full_vector: true` is set, Couchbase {product-name} transparently reranks candidate vectors whenever your {sqlpp} query specifies a similarity function (such as `APPROX_VECTOR_DISTANCE` with Cosine or Euclidean distance).
This recovers near-FP32 accuracy while preserving the memory and latency advantages of binary quantization.

Retaining full-precision vectors increases storage footprint compared to quantized-only storage and adds a minor reranking overhead during query execution.
