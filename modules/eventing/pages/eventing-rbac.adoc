[#description]
== RBAC Overview

Couchbase Server uses Role-Based Access Control (RBAC) to control what each user can do.
Each role grants privileges on specific resources.
You can assign a role to a user directly, or assign it to a group that the user belongs to.
A user can be an administrator or an application.
You can assign roles in the Couchbase Server Web Console or with the REST API.

For more information, see xref:learn:security/authorization-overview.adoc[Authorization] and xref:learn:security/roles.adoc[Roles].

[#eventing-roles]
== Eventing Roles

The following roles control access to the Eventing Service:

[cols="1,3"]
|====
| Role | Access

| Full Admin
| Full access to every resource in the cluster, including all Eventing Functions.
This role can also create users and change their roles.

| xref:learn:security/roles.adoc#eventing-full-admin[Eventing Full Admin]
| Full access to every resource that the Eventing Service needs, including all Eventing Functions.
This role cannot create users or change their roles.

| xref:learn:security/roles.adoc#eventing-manage-functions[Eventing Manage Scope Functions]
| Access to the Eventing Functions in the scopes that you choose when you grant the role.
|====

Couchbase Server 7.0 introduced the Eventing Full Admin role.
In earlier versions, Eventing Functions always ran with Full Admin privileges.
Assign Eventing Full Admin instead of Full Admin to users who only manage Eventing, so they cannot create users or escalate privileges.

[#function-scope]
== Function Scope

A Function Scope is a `bucket.scope` combination that groups Eventing Functions for access control.

Only users with the Full Admin or Eventing Full Admin role can set the Function Scope to `+*.*+`.
All other users must set the Function Scope to an existing `bucket.scope` that their Eventing Manage Scope Functions role covers.
This keeps each user's Functions separate from other users' Functions.

include::cloud:eventing:partial$rbac-warning.adoc[]

Set the Function Scope to the `bucket.scope` that holds the Function's source collection.
Otherwise, removing a Function Scope that points to a resource the Function does not need can undeploy the Function by accident.

NOTE: A user can have more than 1 Eventing Manage Scope Functions role.
If any of these roles matches the Function Scope of an existing Eventing Function, the user can manage, change, or delete that Function, even if another user created or imported it.

IMPORTANT: When you upgrade from a version earlier than 7.1, Couchbase Server sets the Function Scope of every existing Eventing Function to `+*.*+` and runs the Function as a privileged user.
This keeps your existing Functions running after the upgrade.

[#privileged-users]
== Privileged Users

A user with the Full Admin or Eventing Full Admin role has every privilege that the Eventing Service needs on every resource in the cluster.
This user can create and manage any Eventing Function and can set the Function Scope to `+*.*+`.

[#non-privileged-users]
== Non-Privileged Users

A user without the Full Admin or Eventing Full Admin role needs roles that cover each resource their Functions use.

TIP: Assign roles to a group instead of to each user.
You can then reuse the group for other users.

[#minimal-eventing-rbac-role]
=== Minimal Eventing Roles

To create and manage Eventing Functions, a non-privileged user needs at least the following roles:

[cols="1,2"]
|====
| Role | Resource

| Data Reader
| The Eventing storage keyspace

| Data Writer
| The Eventing storage keyspace

| Data DCP Reader
| The source keyspace

| Eventing Manage Scope Functions
| The Function Scope, as a `bucket.scope` or a `bucket`
|====

[#additional-roles]
=== Additional Roles

Depending on what your Functions do, a non-privileged user might also need the following roles:

* Data Reader and Data Writer on the source keyspace.
* Data Monitor on the source keyspace and the Eventing storage keyspace.
* Data Reader and Data Writer on the keyspace of each bucket alias, if the Function has bucket bindings.
* Query Select on the source keyspace, if the Function runs {sqlpp} statements.

== Multi-Tenancy in Eventing

The Function Scope works with the Eventing Manage Scope Functions role to keep tenants separate in both the Web Console and the REST API.
A tenant can be a company department, such as sales or support.

[#jwt-authentication]
== RBAC with JWT Authentication

[.status]#Couchbase Server 8.5#

Couchbase Server 8.5 and later supports JSON Web Token (JWT) authentication for Eventing, in addition to Basic Authentication and mutual TLS (mTLS).
JWT authentication provides short-lived sessions, and matches the JWT support in the Index, Query, Backup, and XDCR services.

To use JWT authentication, pass a bearer token in the `Authorization` header of each REST API request.

JWT authentication has 2 provisioning modes:

* `jitProvisioning=true`: Couchbase Server provisions the user just in time (JIT) from an external identity provider (IdP).
* `jitProvisioning=false`: the user already exists in Couchbase Server RBAC.

[NOTE]
====
With `jitProvisioning=true`, you cannot create, import, or delete Eventing Functions through the REST API.
All other Eventing REST API operations still work.

Use 1 of the following authentication methods to create, import, or delete Eventing Functions:

* Basic Authentication
* mTLS
* JWT authentication with `jitProvisioning=false`

In all cases, the user must exist in Couchbase Server RBAC and have at least the <<minimal-eventing-rbac-role,minimal Eventing roles>>.
====

== Certificate Revocation Checks

////

Eventing checks Certificate Revocation Lists (CRLs) on its connections to other nodes in the cluster.
For more information, see xref:learn:security/certificate-revocation.adoc[Certificate Revocation].

[NOTE]
====
Eventing does not apply CRL checks to connections that the following handler functions make:

* xref:eventing-language-constructs.adoc#n1ql_call[`N1qlQuery()`]
* xref:eventing-language-constructs.adoc#analytics_call[`AnalyticsQuery()`]
* xref:eventing-language-constructs.adoc#search_call[`searchQuery()`]

These functions connect through a shared client library that does not support CRL checks.
They can still connect to a Query, Analytics, or Search Service node that has a revoked certificate.
Eventing applies CRL checks to all its other connections.
====
