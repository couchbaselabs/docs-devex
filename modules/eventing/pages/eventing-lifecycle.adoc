This page walks you through creating an Eventing Function that logs the ID of each document it processes.
You then deploy the Function and move it through each lifecycle operation in the Couchbase Web Console.

For more complex use cases, see xref:eventing-examples.adoc[Eventing Examples].

[#lifecycle-states]
== Eventing Function States

An Eventing Function is always in 1 of the following states:

// TODO(writer): confirm the full list of states and descriptions for 8.5 with Hiren (Eventing). The resuming state was added in 8.0 (see DOC-14268).
[cols="1,3"]
|====
| State | Description

| Undeployed
| The Function exists but does not process mutations.
You can edit its JavaScript code and settings.

| Deploying
| The Function is starting on all Eventing nodes.

| Deployed
| The Function processes mutations from its source keyspace.

| Pausing
| The Function is saving a checkpoint before it stops processing.

| Paused
| The Function has stopped processing and saved a checkpoint.
You can edit its JavaScript code and settings.

| Resuming
| The Function is restarting from its saved checkpoint.

| Undeploying
| The Function is stopping on all Eventing nodes.
|====

For more information about each operation, see the Operations section in xref:eventing-Terminologies.adoc[Terminology].

[#load-sample-data]
=== Load the Sample Data

The Eventing Function in this example listens to the `beer-sample._default._default` keyspace.

To load the `beer-sample` sample bucket:

. In the Couchbase Web Console, go to menu:Settings[Sample Buckets].
. Select *beer-sample*.
. Click btn:[Load Sample Data].

[#create-storage-keyspace]
=== Create the Eventing Storage Keyspace

The Eventing Service stores checkpoints and other configuration documents for your Function in the Eventing storage keyspace.
Make sure this collection is 100% memory-resident, and use it only for the Eventing Service.

To create a bucket, scope, and collection for Eventing storage:

. In the Couchbase Web Console, go to the *Buckets* page.
. Click btn:[Add Bucket].
. In *Name*, enter `rr100`.
. In *Memory Quota*, enter `100` MiB.
. Click btn:[Add Bucket].
. In the `rr100` bucket row, click *Scopes & Collections*.
. Click btn:[Add Scope].
. In *Name*, enter `eventing`.
. Click btn:[Save].
. In the `eventing` scope row, click *Add Collection*.
. In *Name*, enter `metadata`.
. Click btn:[Save].

The *Buckets* page now lists 2 buckets:

image::addfunc_00_prerq_bkts.png["The Buckets page listing the beer-sample and rr100 buckets",100%]

The `eventing` scope in the `rr100` bucket contains the `metadata` collection:

image::addfunc_00_prerq_bkts_s_c.png["The Scopes & Collections page for rr100, showing the metadata collection in the eventing scope",100%]

TIP: You can share 1 Eventing storage collection across all the Eventing Functions for the same tenant.
To keep Functions separate by group or tenant, create a scope and collection for each.

[#eventing_examples_preparations]
== Create an Eventing Function

The *Add Function* dialog contains the following fields:

[cols="1,3"]
|====
| Field | Description

| Function Scope
| The `bucket.scope` combination that groups this Function with other Functions for access control.
Only the Full Admin and Eventing Full Admin roles can set this to `+*.*+`.
For more information, see xref:eventing-Terminologies.adoc#function-scope[Function Scope].

| Listen To Location
| The source keyspace.
The Function runs on every mutation in this keyspace.
You can use the `{asterisk}` wildcard for the scope, the collection, or both, to listen to more than 1 collection.

| Eventing Storage
| The keyspace where the Eventing Service stores the Function's checkpoints and configuration documents.

| Function Name
| A name for the Function.
The name must be unique in the cluster.

| Deployment Feed Boundary
| Whether the Function processes all existing mutations, *Everything*, or only mutations made after deployment, *From now*.
You can change this setting only when the Function is undeployed or paused.

| Description
| Optional text that describes what the Function does.

| Settings
| Logging, worker, timeout, and compatibility settings.
For more information, see xref:eventing-Terminologies.adoc#function-settings[Eventing Function Settings].

| Bindings
| Aliases that connect the Function's code to buckets, URLs, and constants.
For more information, see xref:eventing-Terminologies.adoc#section_mzd_l1p_m2b[Bindings].
|====

To create the Eventing Function:

. In the Couchbase Web Console, go to the *Eventing* page.
. Click btn:[Add Function].
. In *Function Scope*, select `*` for the bucket and `*` for the scope.
. In *Listen To Location*, select `beer-sample` for the bucket, `_default` for the scope, and `_default` for the collection.
. In *Eventing Storage*, select `rr100` for the bucket, `eventing` for the scope, and `metadata` for the collection.
. In *Function Name*, enter `my_evt_function`.
. (Optional) In *Description*, enter `A simple Eventing Function that logs document IDs`.
. Leave *Settings* at the default values.
. Leave *Bindings* empty.
+
This Function only writes to its log, so it needs no bindings.
+
image::addfunc_02_settings.png["The Add Function dialog with the example values entered",484]
. Click btn:[Next: Add Code].
+
The editor contains placeholder code that logs the ID of each document that changes:
+

[source,javascript]
----
function OnUpdate(doc, meta) {
    log("Doc created/updated", meta.id);
}

function OnDelete(meta, options) {
    log("Doc deleted/expired", meta.id);
}
----
+
image::addfunc_03_editor_with_default.png["The Eventing code editor showing the default OnUpdate and OnDelete handlers",100%]
. Click *Eventing* to return to the *Eventing* page.
+
If you change the code, click btn:[Save and Return] instead.

[#exercise-the-eventing-lifecycle]
== Exercise the Eventing Lifecycle

On the *Eventing* page, click `my_evt_function` to show its controls:

image::addfunc_04_newundeployed.png["The Eventing page showing the controls for the undeployed my_evt_function",100%]

The controls change depending on the Function's state:

* *Deploy* and *Undeploy*: start or stop the Function across the cluster.
* *Pause* and *Resume*: stop processing at a checkpoint, then continue from it.
You can pause a Function only when it's deployed.
* *Edit JavaScript* and *View JavaScript*: open the code editor.
You can edit the code only when the Function is paused or undeployed.
* *Log*: show the Function's application log.
* *Export*: download the Function definition as a JSON file.
* *Delete*: remove the Function from the cluster.

[#deploy-function]
=== Deploy the Function

To deploy the Function:

. Click btn:[Deploy].
+
image::addfunc_04a_deploy.png["The Confirm Deploy Function dialog",100%]
. In the *Confirm Deploy Function* dialog, leave *Feed boundary* set to *Everything*.
+
*Everything* processes every existing document in the source keyspace, then each new mutation.
*From now* processes only mutations made after deployment.
. Click btn:[Deploy Function].

The Function status changes to *deploying*.
After the Function finishes bootstrapping, the status changes to *deployed*, and the Function processes all 7,303 documents in `beer-sample`.
It then processes each new mutation as it arrives.

[#pause-function]
=== Pause the Function

Pause a Function to edit its code or settings without missing any mutations.

To pause the Function:

. Click btn:[Pause].
+
image::addfunc_07_pause.png["The Confirm Pause Function dialog",100%]
. In the *Confirm Pause Function* dialog, click btn:[Pause Function].

The Function saves a checkpoint.
Its status changes to *pausing*, then *paused*.

[#resume-function]
=== Resume the Function

To resume the Function:

. Click btn:[Resume].
+
image::addfunc_07_resume.png["The Confirm Resume Function dialog",100%]
. In the *Confirm Resume Function* dialog, click btn:[Resume Function].

The Function status changes to *resuming*, then *deployed*.
The Function continues from its checkpoint, so it does not miss any mutations.

[#undeploy-function]
=== Undeploy the Function

To undeploy the Function:

. Click btn:[Undeploy].
+
image::addfunc_07_undeploy.png["The Confirm Undeploy Function dialog",100%]
. In the *Confirm Undeploy Function* dialog, click btn:[Undeploy Function].

The Function status changes to *undeploying*, then *undeployed*.

=== Delete the Function

NOTE: Eventing Function lifecycle operations and Eventing rebalance are mutually exclusive.
If a lifecycle operation is running, an Eventing rebalance fails.
While an Eventing rebalance is running, you cannot deploy, undeploy, pause, resume, or delete a Function.
