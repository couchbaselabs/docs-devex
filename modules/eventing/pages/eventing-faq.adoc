= Frequently Asked Questions

[#general]
== General

[#mds]
=== Is Eventing an MDS-Enabled Service?

Yes.
Multi-Dimensional Scaling (MDS) isolates workloads in a Couchbase cluster.
You can add Eventing nodes as you add Functions or as mutation rates increase.

[#node-hardware]
=== Which Nodes Work Best for the Eventing Service?

Eventing uses multi-core CPUs efficiently.
Choose nodes for the Eventing Service that have more cores than the nodes you use for the Index Service.

[#co-location]
=== Can the Eventing Service Run on the Same Node as Other Services?

Yes.
You can run the Eventing Service on the same node as other MDS-enabled services.

[#binary-documents]
=== Does Eventing Support Text and Binary Documents?

Yes.
A document's value can be text or binary data.
Most documents contain JSON.
Eventing passes binary documents to your Function only if the Function's language compatibility setting is 6.6.2 or later.

With binary support:

* Eventing Functions can read binary values through a bucket alias or an advanced keyspace accessor.
* The `meta` parameter of `OnUpdate(doc, meta)` has a `datatype` property, set to `binary` or `json`.
This property is not available in `OnDelete(meta, options)` or in basic keyspace accessors.
* The `curl()` function can send binary data to and receive binary data from an external REST endpoint.

For more information, see xref:eventing-Terminologies.adoc#function-settings[Eventing Function Settings].

[#change-capture]
== Change Capture

[#dcp-dedup]
=== Does Eventing See Every Update to a Document?

No.
If a document changes several times in a short time window, the Database Change Protocol (DCP) can deduplicate the changes.
The `OnUpdate` and `OnDelete` handlers receive only the deduplicated events that DCP publishes.

[#scope-of-changes]
=== Can a Function Listen to All Changes in Couchbase Server?

No.
A Function listens only to the changes that DCP publishes for its source collection on the Data Service nodes.
A Function cannot listen to changes in other components, such as the Search Service, Views, or the Index Service, and cannot listen to system events.

[#what-changed]
=== Can You Find Out What Changed in a Document?

No.
Eventing does not track document versions or show which fields changed.
If you need versioning, include it in your data model and application logic.

[#old-new-values]
=== Can You Get the Old and New Values of a Document in a Function?

No.
Eventing does not keep earlier versions of documents.
As a workaround, you can keep a copy of each document in a separate collection that stores the version from before the latest change.
For example designs, see xref:eventing-examples.adoc[Eventing Examples].

[#mutation-order]
=== Does Eventing Process Mutations in Order?

Yes.
Eventing always processes all changes to a document in order.

[#functions]
== Functions

[#vs-triggers]
=== Are Functions Similar to Database Triggers?

Functions are similar to post-triggers in other databases.
When a Function runs, the Data Service has already completed the change.
The `OnUpdate` and `OnDelete` handlers let you define what happens after the change.
A Function sees the change event itself, so it does not map directly to a database trigger.

[#vs-rules-engine]
=== Are Functions Similar to a Rules Engine?

Only partly.
A rules engine enforces ordering and other semantics that Functions do not provide.
A Function lets you run business rules close to the data, but cannot trigger another Function directly.

[#vs-stored-procedures]
=== Are Functions Similar to Stored Procedures?

No.
A stored procedure follows a request-response model and runs only when something calls it.
Functions are event-driven: changes to data trigger them.

[#middleware]
=== Do You Need Middleware to Consume the Changes That Functions Process?

No.
Functions need no additional infrastructure.
The Function itself consumes and acts on mutations.
No SDK or middleware gives programmatic access to the changes that a Function processes.
The Eventing REST API provides administrative operations only.

[#js-libraries]
=== Can You Import Your Own JavaScript Libraries or Node Modules?

No.
Eventing does not support importing Node modules or external JavaScript libraries.
You can define other JavaScript functions in an Eventing Function, outside `OnUpdate` and `OnDelete`, and call them as often as you need.

[#data-service-documents]
=== Which Documents Can Functions Process?

Functions process documents from the DCP stream of the Data Service.
The handler receives the document key as `meta.id`.
`OnUpdate` also receives the document value as `doc`.
`OnDelete` receives only the key.

For more information about document types, see <<binary-documents>>.

[#external-processes]
=== Can Functions Interact with External Processes?

Yes.
Functions can call external REST endpoints over HTTP with the `curl()` function.
Use it to send data changes to other systems, notify applications about events, or enrich documents with data from external resources.

For more information, see xref:eventing-curl-spec.adoc[cURL].

[#debugging]
=== Can You Debug a Function?

Yes.
Eventing provides a debugger, logs, and statistics, which have minimal effect on overall performance and scalability.
When you debug a Function, Eventing sends 1 mutation to the debugger session and keeps processing all other mutations as usual.

For more information, see xref:eventing-debugging-and-diagnosability.adoc[Debugging and Diagnosability].

[#change-in-production]
=== Can You Change a Function While It Runs in Production?

Yes.
Pause the Function, edit it, and then resume it.
The Function does not lose any mutations.

You can also undeploy the Function, edit it, and deploy it with the *From now* feed boundary.
With this approach, the Function can miss mutations.

[#ci-cd]
=== How Do You Run Function Lifecycle Operations from CI/CD?

Use the Eventing REST API to run Function lifecycle operations from scripts and pipelines.

For more information, see xref:eventing-rest-api:index.adoc[Eventing REST API].

[#call-rest-endpoint]
=== How Do You Call a REST Endpoint from a Function?

Use the `curl()` function with a URL binding.

For more information, see xref:eventing-curl-spec.adoc[cURL].

[#vs-kafka]
=== How Do Functions Compare with the Kafka Connector?

Functions run your business logic on the server, with no additional infrastructure or middleware to deploy or manage.
The Couchbase Kafka connector is an SDK component that needs an application container or middleware to run.

[#deploy-per-node]
=== Do You Need to Deploy Functions on Each Eventing Node?

No.
The Eventing Service distributes the Function code and lifecycle requests across all Eventing nodes.

As a best practice, use the Web Console on 1 node only while you develop or change Eventing Functions.
If you edit a Function in 2 browser windows or tabs, you might deploy an earlier version of its code or settings by mistake.

[#retries]
=== How Does Eventing Retry Operations?

Eventing retries transient and recoverable errors every 200{nbsp}ms, 5 times per second, until the Function reaches its script timeout.
The script timeout is 60 seconds by default.

If you set `lcb_retry_count` to a value greater than 0, Eventing stops retrying after that number of retries.
When Eventing runs out of retries, it throws an exception for the operation.

For more information, see xref:eventing-rest-api:index.adoc#settings_schema[Eventing Function settings].

[#function-code]
== Function Code

[#languages]
=== Which Languages Can You Use?

You can use JavaScript, ECMAScript 6, only.
To let Functions shard and scale automatically, Eventing removes some capabilities, such as global state and asynchrony.

For more information, see xref:eventing-language-constructs.adoc#unsupported-lang-features[Unsupported Language Features].

[#global-variables]
=== Why Do Functions Not Support Global Variables?

Global variables would prevent a Function from sharding, scaling, and handling rebalances.
Save any global state to a keyspace that the Function can access through a bucket binding.
For global constants, use a constant binding.

[#meta-parameter]
=== What Does the meta Parameter Contain?

The `meta` parameter of `OnUpdate` and `OnDelete` contains the metadata fields of the document.
It does not show which fields changed.

Document metadata is different from the Eventing storage keyspace, which the Eventing Service uses to store state and checkpoints.

For more information, see xref:learn:data/data.adoc[Data].

[#multiple-functions]
=== Can More Than 1 Function Listen to the Same Collection?

Yes.
You can define several Functions with the same source collection, each with its own business logic.
You cannot control the order in which these Functions run.

Each Function opens its own set of DCP streams.
On a busy system, you get better performance if you combine Functions that share a source collection into 1 Function.
Use a JavaScript `switch` statement or an `if`/`else` block to combine their logic.

[#read-state]
=== Can a Function Read Additional Data?

Yes.
A Function can read related documents by key from any keyspace that it can access through a bucket binding.
A Function can also read data from an external REST endpoint with `curl()`.

[#write-state]
=== Can a Function Change Documents?

Yes.
A Function can write documents to any keyspace that it can access through a bucket binding with *Read Write* access, including its source collection.

[#eventing-storage]
== Eventing Storage Keyspace

[#storage-what]
=== What's the Eventing Storage Keyspace?

The Eventing Service stores metadata, such as checkpoints and timers, in a collection in a xref:learn:buckets-memory-and-storage/buckets.adoc[Couchbase bucket].
This collection is the Eventing storage keyspace, also called the metadata collection.
It makes Eventing more resilient and lets Functions restart on any Eventing node.

Create the metadata collection before you start to use the Eventing Service.
As a best practice, use 1 metadata collection for all Eventing Functions in the cluster.

Follow these guidelines for the metadata collection:

* Enable xref:manage:manage-buckets/create-bucket.adoc[vBucket replicas] so the collection can recover from failures.
* Use the collection only for Eventing.
Do not store other data in it.
* Allow about 2{nbsp}MB for each Function: 1024 documents of 1884 bytes each.
* If a Function uses timers, allow an additional 0.04{nbsp}MB: 256 documents of 196 bytes each.
* For each active timer, allow 832 bytes plus the size of the timer context, up to 1856 bytes.
By default, a timer context can be up to 1024 bytes.
* Each timer uses up to 3 documents: root, alarm, and context.
Some timers use only 2 additional documents, because they share a root document with an earlier timer.

Keep timer contexts small.
Store a reference to a document in the context instead of the whole document.
You can change the maximum context size for each Function with the `timer_context_size` setting.
For more information, see xref:eventing-rest-api:index.adoc#settings_schema[Eventing Function settings].

For more information about sizing and placing the metadata collection, see xref:eventing-buckets-to-collections.adoc[Buckets vs Collections].

[#storage-cancel-timers]
=== Why Doesn't the Metadata Collection Shrink When You Cancel Timers?

When you cancel or overwrite a timer, Eventing deletes its context document at once.
Eventing deletes the timer's alarm document and root document later, at the time the timer was originally scheduled to fire.
Each vBucket has 1 root document for each scheduled time.

Suppose you schedule 100,000 timers to fire in 1 year and then cancel them.
Up to 2 documents for each timer then remain until that date.

[#timers]
== Timers

[#timer-delays]
=== Why Do Timers Fire Later Than the Scheduled Time?

The timer implementation handles millions of distributed timers.
It never loses a timer, and it runs each timer as soon as possible after its scheduled time.

In a steady state, timers fire about 3 to 4 seconds after their scheduled time.
If you schedule a timer close to the current time, the delay can increase to about 14 seconds.

For more information, see the Wall-clock Accuracy section of xref:eventing-timers.adoc[Timers].

[#cancel-timer]
=== Can You Cancel a Timer?

Yes.
Call the `cancelTimer()` function, or create a new timer with the same reference as the existing timer.

For more information, see xref:eventing-timers.adoc#canceltimer-function[cancelTimer()].

[#recurring-timers]
=== Can You Create a Recurring Timer?

Yes.
A timer callback can create new timers.

For more information, see xref:eventing-timers.adoc[Timers].

[#future-timers]
=== Can You Schedule a Timer Far in the Future?

Yes.
You can schedule timers days, weeks, or years in the future with no performance effect on an otherwise idle Eventing system.

[#resume-burst]
=== Why Does Bucket Activity Increase When You Resume a Function with Timers?

Resuming a Function with timers after a long pause, such as several days, causes a burst of activity.
The activity occurs in the bucket that holds the metadata collection.
The Function also stops processing mutations until it finishes scanning its timers.
The delay is proportional to the length of the pause.

[#timer-bindings]
=== Can You Pass a Binding in a Timer's Context?

No.
Bucket bindings and URL bindings are not serializable and exist only in the V8 worker that runs the Function.
A timer can fire on a different thread.

The timer's callback can use the binding directly.
You can also pass a constant binding in a timer's context.

[#timer-functions]
=== Can You Pass a JavaScript Function in a Timer's Context?

No.
A JavaScript function is a memory reference in 1 V8 worker, so it's not serializable.
A timer can fire on a different thread.

The timer's callback can call the function directly.
You can also pass the function's name in the context and call it with the JavaScript `eval` method.

[#cluster-behavior]
== Cluster Behavior

[#failover]
=== What Happens to Eventing During a Failover?

When a Data Service node fails over, the cluster can lose some mutations, and the Eventing Service does not process them.
When an Eventing node fails over, Eventing can process some mutations more than once.

[#rebalance-events]
=== Does a Rebalance Affect Event Processing?

No.
Functions do not lose any mutations during a rebalance.

[#rebalance-lifecycle]
=== When Can You Rebalance Eventing Nodes with Deployed Functions?

Function lifecycle operations and Eventing rebalances are mutually exclusive.
Lifecycle operations include:

* Deploy and undeploy
* Pause and resume
* Delete

If a lifecycle operation is running, an Eventing rebalance fails.
While an Eventing rebalance is running, you cannot run a lifecycle operation.

[#performance]
=== How Do You Improve the Performance of a Function?

Use 1 or more of the following approaches:

* Add workers in the Function's settings to improve the performance of that Function.
New Functions use 1 worker by default.
* Add an Eventing node and rebalance.
Each Eventing node handles a subset of vBuckets, which improves performance for all Functions.
* Scale the Data Service, because its performance can limit a Function.

For more information about sizing workers, see xref:troubleshooting-best-practices.adoc[Troubleshooting and Best Practices].

[#worker-stall]
=== Why Does Processing Stall with a Large Number of Workers?

With more than about 48 workers, a Function's processing can stall.
This problem depends on the workload and occurs most often when the Function updates its source collection.
The cause is a lack of resources for the Eventing Service.

To fix it, increase the Eventing memory quota in the cluster settings, for example from the 256{nbsp}MB default to 512{nbsp}MB.
This is 1 of the rare cases where you need to increase the Eventing memory quota.

The number of cores on the Eventing node and the performance of the Data Service can also limit a Function.
In these cases, add compute power or nodes to the Eventing Service, or scale the Data Service.

For more information, see xref:eventing-memory-quota.adoc[Eventing Service Memory Quota].

[#node-to-node-encryption]
=== Does Eventing Support Node-to-Node Encryption?

Yes.

Pause all deployed Eventing Functions before you turn node-to-node encryption on or off, and resume them after the change.
Pausing prevents the loss of mutations during the change.
