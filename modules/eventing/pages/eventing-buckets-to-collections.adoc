[#data-hierarchy]
== Data Organization

Couchbase Server organizes data in the following hierarchy:

* Cluster
** Bucket
*** Scope
**** Collection
***** Document

A bucket contains scopes, a scope contains collections, and a collection contains documents.
Every bucket has a `_default` scope that contains a `_default` collection.

In Couchbase Server versions earlier than 7.0, documents existed directly in buckets, with no scopes or collections.

For more information, see xref:learn:data/scopes-and-collections.adoc[Scopes and Collections].

[#scopes-and-collections]
== Scope and Collection Design

Use a scope as the unit you allocate to an application, a customer, or a team:

* If the cluster supports several internal applications, give each application its own scope.
* If the cluster serves several client organizations that each run a copy of an application, give each copy its own scope.
* If development or test groups share the cluster, give each group its own scope.

The owner of a scope can then create the collections they need in it.

Use collections to group documents of the same type.
Create separate `products`, `orders`, and `customers` collections instead of storing all 3 document types in 1 bucket with a `type` field.
You can then query a single collection instead of the whole bucket and grant access at the collection level.

For more information about access control, see xref:eventing-rbac.adoc[Eventing Role-Based Access Control].

[#migrate-to-collections]
== Migrate from Buckets to Collections

In versions earlier than 7.0, applications stored different types of documents in the same bucket and used a `type` property to tell them apart.
The following examples show shortened documents:

[source,json]
----
{
  "id": 10025,
  "type": "hotel",
  "brand": "Hilton"
}
----

[source,json]
----
{
  "id": 10,
  "type": "airline",
  "iata": "Q5"
}
----

When you upgrade, a bucket's documents move to its `_default._default` collection, so you do not need to reorganize your data.
For example, a bucket named `travelinfo` becomes the keyspace `travelinfo._default._default`.

You can then split the documents into collections by type.
For example, you can move airline documents to `travelinfo.data.airline` and hotel documents to `travelinfo.data.hotel`.

TIP: You can use an Eventing Function to migrate a bucket into a set of collections.
For an example that migrates the `beer-sample` bucket, see xref:eventing-handler-ConvertBucketToCollections.adoc[Function: Convert Bucket to Collections].

[#benefits]
=== Benefits of Collections

Organizing documents into collections has the following benefits:

* You no longer need a `type` property to tell document types apart.
* {sqlpp} queries, XDCR, and backup and restore can work on individual collections.
* Indexing is more efficient because the Data Service sends only documents from specific collections to the Index Service.
* Queries are simpler because statements can target a specific collection.
* Migration from relational databases is easier because collections can map to existing tables.
* You can authorize each application to use only the collections it needs.

[#eventing-keyspaces]
== Organize Eventing Keyspaces

An Eventing Function can keep using the `_default` scope and collection and run without changes after an upgrade.
To use fewer resources or increase throughput, you can reorganize your keyspaces.

Eventing performance depends on the residency of the bucket that holds the Eventing storage collection.
Put the Eventing storage collection in a bucket that's 100% memory-resident, separate from your bulk data.

[#single-tenancy]
=== Single-Tenant Layout

In a single-tenant cluster, 1 application or organization owns all the data.
The following diagram shows a recommended layout:

image::eventing-collections-single-tenant.jpg["Single-tenant layout: an rr100 bucket at 100% residency holds the eventing and profiles scopes, and a bulk bucket at 20% or more residency holds the logistics and profiles scopes",100%]

* The `rr100` bucket is 100% memory-resident.
Its `eventing` scope holds the `metadata` collection for Eventing storage and the `lkuptable` collection for lookup data.
* The `bulk` bucket has a residency of 20% or more and holds the business data, such as the `orders` and `shipments` collections in the `logistics` scope.
* The `profiles` scope exists in both buckets.
Frequently accessed collections, `active` and `provision`, stay in `rr100`.
Less frequently accessed collections, `suspended` and `archived`, go in `bulk`.

[#multi-tenancy]
=== Multi-Tenant Layout

In a multi-tenant cluster, each customer gets its own scope in each bucket.
The following diagram shows a recommended layout:

image::eventing-collections-multi-tenant.jpg["Multi-tenant layout: the rr100 and bulk buckets each contain 1 scope per customer, cust1 to custN",100%]

* In the `rr100` bucket, each customer scope, `cust1` to `custN`, has its own `metadata` and `lkuptable` collections.
* In the `bulk` bucket, each customer scope has its own `orders` and `shipments` collections.

This layout keeps each customer's data and Eventing storage separate.

=== Size the Eventing Storage Collection

Eventing performance can drop by a factor of 5 or more when the Eventing storage collection shares a bucket with partly resident data.

You can keep all collections, including Eventing storage, in 1 bucket.
If that bucket is 100% resident, performance does not suffer.
As residency drops, Eventing reads its control documents from disk instead of memory.
Control documents include Function definitions, timers, and checkpoints.

Without timers, the Eventing storage collection stays small.
Each Function stores 1 checkpoint document per vBucket, plus occasional additional checkpoint documents.
If your Functions use timers, the collection also grows with the number of active timers.
