[#upgrades]
== Upgrades

[#pause-before-upgrade]
=== Pause Functions Before a Rolling Upgrade

In Couchbase Server 8.0 and earlier, running Eventing Functions during a rolling upgrade increases rebalance duration.

To reduce rebalance time:

. Pause all your Eventing Functions before you start the upgrade.
. Resume your Eventing Functions after the upgrade completes.

[#workers]
== Workers

[#configure-workers]
=== Configure the Number of Workers

Each Eventing Function uses 1 worker by default.
You can configure up to 64 workers for a Function, and Couchbase Server prevents you from creating a Function that exceeds this limit.
Upgrades keep the number of workers that you configured for each Function.

Add workers when a Function needs more throughput.
For example, a Function that makes `curl()` calls to slow REST endpoints, slower than 20{nbsp}ms, is I/O bound rather than CPU bound.
More workers let it run more calls in parallel.

When you deploy or resume a Function, Couchbase Server calculates a worker threshold based on the node's resources.
If the total number of workers exceeds this threshold, Couchbase Server shows a warning but still deploys the Function:

[source,text]
----
There are 104 eventing workers configured to run on 24 cores. A sizing exercise is recommended.
----

Follow these guidelines when you size workers across all your Eventing Functions:

* Do not configure more than 4 times the number of physical cores, or 2 times the number of vCPUs.
* If every Function has high throughput, do not configure more workers than the number of physical cores.

For more information, see xref:eventing-Terminologies.adoc#function-settings[Eventing Function Settings].

[#error-handling]
== Error Handling

[#try-catch]
=== Use Try-Catch Blocks

Use `try`/`catch` blocks with `log()` statements in your Function's JavaScript code for error handling and debugging.

Before deployment, Couchbase Server checks the Function's code and deploys only valid Functions.
Runtime errors can still occur.
Without a `try`/`catch` block, the application log records only a summary of each exception once a minute for each worker.
With a `try`/`catch` block, you can log each error and its details to the Function's application log.

// TODO(writer): confirm with Hiren (Eventing) how uncaught runtime errors appear in the system log and the application log in 8.5.
// The original page said runtime errors go to the system log and that application logs do not capture exceptions by default.

The following example logs any error that the write operation throws:

[source,javascript]
----
function OnUpdate(doc, meta) {
    log('document', doc);
    try {
        var time_rand = random_gen();
        dst_col[meta.id + time_rand] = doc;
    } catch(e) {
        log(e);
    }
}
----

NOTE: Each Eventing node writes its own application log file, which contains only the mutations that the node processed.

For more information, see xref:eventing-debugging-and-diagnosability.adoc#application-logs[Application Logs].

[#cyclicredun]
== Recursive Mutations

Eventing Functions can write data, and each write is a mutation that other Functions can process.
To avoid cyclic data changes, plan which collections each Function reads from and writes to.

[#infinite-recursion]
=== Avoid Infinite Recursion

Make sure that a series of Eventing Functions does not cause cyclic mutations, where writes from 1 Function trigger another Function in a loop.

The following design causes infinite recursion:

* `functionA` has source `collectionA` and writes to `collectionB` through a binding with the same alias:
+
[source,javascript]
----
function OnUpdate(doc, meta) {
    collectionB[meta.id] = {"status":"updated by functionA"};
}
----
* `functionB` has source `collectionB` and writes to `collectionC`:
+
[source,javascript]
----
function OnUpdate(doc, meta) {
    collectionC[meta.id] = {"status":"updated by functionB"};
}
----
* `functionC` has source `collectionC` and writes to `collectionA`:
+
[source,javascript]
----
function OnUpdate(doc, meta) {
    collectionA[meta.id] = {"status":"updated by functionC"};
}
----

A single mutation in `collectionA` starts an endless loop through `collectionB` and `collectionC` and back to `collectionA`.

To break the loop, use 1 of the following approaches:

* Change `functionC` to write to a different collection, such as `collectionD`:
+
[source,javascript]
----
function OnUpdate(doc, meta) {
    collectionD[meta.id] = {"status":"updated by functionC"};
}
----
* Change `functionA` to ignore documents that `functionC` updated:
+
[source,javascript]
----
function OnUpdate(doc, meta) {
    if (doc["status"] == "updated by functionC") return;
    collectionB[meta.id] = {"status":"updated by functionA"};
}
----

Couchbase Server detects short recursive loops.
A long chain of source and destination collections across several Functions can still create recursion that Couchbase Server does not detect.
Identify and avoid these chains in your design.

As a best practice, do not configure other Eventing Functions to listen to the collections that your Function writes to.

[#self-recursion]
=== Direct Self-Recursion

An Eventing Function can write back to its own source collection, for example to enrich documents.
To do this, create a read-write bucket binding to the source collection.
The Eventing Service detects and suppresses the mutations that these writes cause.

This suppression applies only to writes through the binding's JavaScript map.
It does not apply to mutations from {sqlpp} statements.

The following example comes from Case 2 of xref:eventing-example-data-enrichment.adoc[Data Enrichment].
The Function `functionDirectEnrich` has source `collectionA` and writes back to `collectionA` through the alias `src`:

[source,javascript]
----
function OnUpdate(doc, meta) {
  log('document', doc);
  doc["ip_num_start"] = get_numip_first_3_octets(doc["ip_start"]);
  doc["ip_num_end"]   = get_numip_first_3_octets(doc["ip_end"]);
  // !!! write back to the source collection !!!
  src[meta.id]=doc;
}
function get_numip_first_3_octets(ip) {
  var return_val = 0;
  if (ip) {
    var parts = ip.split('.');
    //IP Number = A x (256*256*256) + B x (256*256) + C x 256 + D
    return_val = (parts[0]*(256*256*256)) + (parts[1]*(256*256)) + (parts[2]*256) + parseInt(parts[3]);
    return return_val;
  }
}
----

[#recursionchecks]
=== Turn Off Infinite Recursion Checks

Avoid recursive loops where you can.
If you must allow them, you can turn off the recursion checks.

For example, if you run xref:eventing-handler-ConvertBucketToCollections.adoc[Function: Convert Bucket to Collections] with the same bucket as source and target, the Function fails with an `ERR_INTER_FUNCTION_RECURSION` error.

To turn off recursion checks, send the following request to any Eventing node.
You need administrator privileges.

[source,sh]
----
curl -X POST -u $CB_USERNAME:$CB_PASSWORD http://$HOST:8091/_p/event/api/v1/config \
  -d '{"allow_interbucket_recursion":true}'
----

To turn recursion checks back on, send the following request:

[source,sh]
----
curl -X POST -u $CB_USERNAME:$CB_PASSWORD http://$HOST:8091/_p/event/api/v1/config \
  -d '{"allow_interbucket_recursion":false}'
----

[#eventing-storage]
== Eventing Storage Keyspace

[#storage-residency]
=== Keep the Eventing Storage Keyspace 100% Memory-Resident

If the Eventing storage keyspace is not fully memory-resident, Eventing reads its metadata from disk.
Eventing can then stall, run much slower, fail, or miss mutations.

Give the bucket that holds the Eventing storage keyspace enough memory quota for a 100% residency ratio.

For more information about placing and sizing the Eventing storage keyspace, see xref:eventing-buckets-to-collections.adoc[Scopes and Collections in Eventing].

[#ephemeral-buckets]
=== Use Ephemeral Buckets Only for User Data

You can use Ephemeral buckets for your Function's source keyspace and for keyspaces in bucket bindings.
The Eventing storage keyspace must be in a Couchbase bucket, which persists its data.

If the Eventing storage keyspace is in an Ephemeral bucket, the Data Service evicts timer and checkpoint documents when the bucket reaches its quota.
Eventing can then lose track of timers and of the mutations that it processed.

WARNING: Never delete the Eventing storage collection.
Make sure that no Eventing Function code or other service writes to or deletes documents from it.

[#troubleshooting]
== Troubleshoot Common Problems

[#timeout-increase]
=== Sudden Increase in Timeouts

A sudden increase in the timeout statistic has 1 of 2 common causes:

* The Function's execution time increased.
Higher execution latency leads to a Function backlog and to failures.
* The script timeout is too low for the Function's execution latency.

To fix the problem:

. Measure the Function's execution latency.
. Increase the script timeout to match.
. Use `try`/`catch` blocks and application logs to monitor and debug errors in the Function.

For more information, see xref:eventing-statistics.adoc[Statistics].

[#lcb-etmpfail]
=== Temporary Failure Errors

If a Function that ran without problems starts to throw temporary failure (`LCB_ETMPFAIL`) errors, the residency ratio of its source or destination collection has probably dropped.
The source and destination collection can be the same collection.
A low residency ratio can stop the system from handling the rate of mutations and the reads and writes that the Function needs.

The application log shows an error similar to the following:

[source,text]
----
2020-03-13T11:46:32.383-07:00 [INFO] "Exception: " {"message":{"code":392,"desc":"Temporary failure received from server. Try again later","name":"LCB_ETMPFAIL"},"stack":"Error\n    at OnUpdate (MyEventingFunction.js:177:25)"}
----

This error means that the system does not have enough resources for the load.
Eventing retries the failed Data Service operation every 200{nbsp}ms until the Function reaches its script timeout.
If you set `lcb_retry_count`, Eventing stops after that number of retries instead.
When the retries run out, the Function, `MyEventingFunction` in this example, throws an `LCB_ETMPFAIL` error from `libcouchbase`.
For more information about retries, see xref:eventing-faq.adoc[Frequently Asked Questions].

Do not catch this error and retry the same operation in your Function, because retries make the problem worse.
Your Function can take other actions, such as sending a notification.

At more than 12,000 mutations per second, a Function can have problems when the residency ratio falls to less than 18%.
This threshold varies with factors such as the number of mutations and the storage type.

TIP: Watch the number of documents and the residency ratio of your source, Eventing storage, and destination collections.
Growth in your dataset can lower the residency ratio over time.

To fix the problem, use 1 of the following solutions:

* Increase the memory quota of the collection's bucket to raise the residency ratio.
* Remove the resource bottleneck: add Data Service nodes, use faster disk I/O, and increase memory.

[#regex-quotes]
=== Regular Expressions with Quotes Fail to Deploy

The Eventing Service parser rejects unescaped quotes in regular expression literals, even though JavaScript allows them.
Always escape single and double quotes in a regular expression with a backslash (`\`).

The following regular expression contains unescaped quotes and fails:

[source,javascript]
----
mystring.match(/(\S+)[^=]=["']?((?:.(?!["']?\s+(?:\S+)[^=]=|[>"']))+.)["']?/g);
----

The following regular expression escapes the quotes and works:

[source,javascript]
----
mystring.match(/(\S+)[^=]=[\"\']?((?:.(?![\"\']?\s+(?:\S+)[^=]=|[>\"\']))+.)[\"\']?/g);
----
