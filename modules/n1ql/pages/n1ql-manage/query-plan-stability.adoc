= Query Plan Stability
:page-topic-type: concept
:page-status: Couchbase Server 8.5
:page-edition: Enterprise Edition
:page-toclevels: 2
:description: Query Plan Stability enables you to save and reuse query plans across upgrades.

[abstract]
{description}

== Overview

Query Plan Stability (or Plan Stability) preserves query execution plans across Couchbase Server upgrades by saving plans to persistent storage. 

By default, the Query Service caches execution plans for prepared statements in memory. 
When a query node restarts or when you upgrade Couchbase Server, the Query Service clears this in-memory cache. 
This forces the query optimizer in the new version to regenerate a plan for the same query.
The new plan can differ from the original plan and cause unexpected performance changes.

When you enable Plan Stability, the Query Service automatically saves execution plans to a persistent storage bucket. 
After an upgrade or restart, the service reloads and reuses these saved plans to maintain consistent query performance.

== Key Benefits

Plan Stability provides the following benefits: 

* Queries can run with same plans before and after upgrades.
* Reduces the risk of performance degradation from plan changes.
* Protects applications tuned for specific query plans.

== Plan Stability Modes

Plan Stability supports 4 operating modes:

[cols="1,3", options="header"]
|===
|Mode |Description

|`Off`
|Does not save execution plans to persistent storage.
The Query Service generates a new plan for every statement execution.

|`On Prepared Statements`
|Saves execution plans to persistent storage only for prepared statements.
The Query Service generates a new plan for every ad hoc query.

|`On All Statements`
|Saves execution plans to persistent storage for all queries, including prepared statements and ad hoc queries.

|`Frozen`
|Does not save execution plans to persistent storage for new queries, but uses existing saved plans for matching queries.
|===

You can configure these modes at the cluster level using the Couchbase Web Console or the `system:settings` catalog.
These settings apply across all query nodes in your cluster.
For information about how to configure these settings, see <<configure-plan-stability>>.

NOTE: The table shows the mode names as they appear in the Couchbase Web Console.
For the corresponding `system:settings` values, see xref:n1ql:n1ql-intro/sysinfo.adoc#sys-settings[Monitor Settings].

In addition, you can also configure Plan Stability for individual queries.
When you create a prepared statement using `PREPARE`, include the keyword `SAVE` to save the plan to persistent storage.

== How Plan Stability Works

Plan Stability saves, reloads, and validates execution plans using the following steps. 

[discrete]
=== Step 1: Plan Generation and Persistence

When you run a query, the Query Service evaluates the statement type and the active Plan Stability configuration, as described in <<plan-stability-modes,Plan Stability Modes>>.

When Plan Stability is active for ad hoc queries, the Query Service automatically converts the query into a prepared statement (using xref:n1ql:n1ql-language-reference/prepare.adoc#auto-prepare[auto-prepare]) before saving the plan.

For prepared statements, you can save a plan regardless of the cluster setting by including `SAVE` in the `PREPARE` statement.

The Query Service stores all saved plans in the `QUERY_METADATA` bucket.
For more information, see <<storage>>.

[discrete]
=== Step 2: Plan Reload

After a Couchbase Server upgrade or restart, the Query Service reloads plans from `QUERY_METADATA` directly into memory.
When you submit a query, the service checks if a matching plan exists.

To view saved plans, use the `system:prepareds` catalog.
For more information, see <<view-saved-plans>>.

[discrete]
=== Step 3: Plan Validation and Error Handling

Before executing a saved plan, the Query Service verifies if all dependencies (such as indexes and keyspaces) still exist.
If the validation fails, the service handles the query according to your configured error policy.
For more information, see <<error-policies>>.

If the validation succeeds, the Query Service executes the query using the saved plan.

== Storage 

The Query Service stores saved execution plans in a dedicated, user-level bucket called `QUERY_METADATA`. 
The default memory quota of the bucket is 100 MB.

The Query Service automatically creates this bucket when you do 1 of the following:

* Run a `PREPARE` statement with the `SAVE` keyword.
* Set Plan Stability to `On Prepared Statements`, `On All Statements`, or `Frozen`.

If you drop the bucket, the service automatically recreates it the next time these actions occur.

[NOTE]
====
* Users with admin privileges can drop the `QUERY_METADATA` bucket.
* Dropping the bucket manually can trigger runtime errors during query execution.
* Setting the Plan Stability mode to `Off` does not automatically drop the bucket.
* Users with admin privileges must monitor and adjust the memory quota for the `QUERY_METADATA` bucket to prevent low memory residency. 
====

== Error Policies

Before running a saved query plan, the Query Service verifies whether the plan is still valid.
A saved plan can become invalid over time. 
For example, if an index used in the plan is dropped, the plan becomes invalid and cannot be used. 
When plan verification fails, the Plan Stability error policy determines how the service responds.

Plan Stability supports the following error policies:

[cols ="1,3", options="header"]
|===
| Error Policy | Description

| `Strict` 
| Stops statement execution and returns an error to the application. 

| `Moderate`
| Reprepares the statement to generate and run a new plan. 
The original saved plan remains unchanged. 

This policy is useful when an index becomes temporarily unavailable. 
Statement executions might use a suboptimal plan while the index is down, but the saved plan stays intact, and you can reuse it once the index becomes available. 

| `Flexible`
| Reprepares the statement to generate a new plan and replaces the saved plan with the new one.  

This behavior is similar to the standard prepared statement handling.
|===

For information about how to set the error policy, see <<configure-plan-stability>>.

== Configure Plan Stability

You can configure plan stability using 1 of the following methods:

** <<using-the-couchbase-web-console>>
** <<using-the-system-settings-catalog>>
** <<using-the-prepare-statement>>

=== Using the Couchbase Web Console

When you configure Plan Stability in the Couchbase Web Console, settings apply automatically to every query node in your cluster. 

. In the Couchbase Web Console, go to menu:Settings[Query].

. From the *Plan Stability* list, select a mode.
For a list of available modes, see <<plan-stability-modes>>.

. From the *Plan Stability Error Policy* list, select an error policy.
For a list of available policies, see <<error-policies>>.

. Click btn:[Save].

=== Using the System Settings Catalog

To configure Plan Stability programmatically, run an `UPDATE` statement against the `system:settings` catalog.
These settings apply at the cluster level to every query node in your cluster.

To set the Plan Stability mode, use the following query: 

[source,sqlpp]
----
UPDATE system:settings SET plan_stability.mode = "off";
----

To set the Plan Stability error policy, use the following query: 

[source,sqlpp]
----
UPDATE system:settings SET plan_stability.error_policy = "moderate";
----

For a list of acceptable values for `plan_stability.mode` and `plan_stability.error_policy`, see xref:n1ql:n1ql-intro/sysinfo.adoc#sys-settings[Monitor Settings].

=== Using the PREPARE Statement

You can also configure Plan Stability for individual queries.
When you create a prepared statement using `PREPARE`, include the keyword `SAVE` to save the plan to persistent storage.

* With `SAVE`: Saves the execution plan to persistent storage. 
* Without `SAVE`: Keeps the execution plan in memory only. 

The following example shows how to use `SAVE`: 

[source,sqlpp]
----
PREPARE SAVE get_route_by_airline FROM
SELECT * FROM route
WHERE airline = "FL";
----

For more information, see the xref:n1ql:n1ql-language-reference/prepare.adoc[PREPARE] statement.

== View Saved Plans

To view all saved execution plans, use the `system:prepareds` catalog.

If you want to retrieve a specific saved plan from the list, use its plan name:

* For prepared statements, the plan name matches the name you specify in the `PREPARE` statement.

* For ad-hoc queries, the Query Service generates a plan name automatically from the statement text. 

To view all saved plans, use the following query:

[source,sqlpp]
----
SELECT *, meta().plan FROM system:prepareds;
----

To find the saved plan for a specific ad-hoc query, filter by the statement text:

[source,sqlpp]
----
SELECT *, meta().plan FROM system:prepareds WHERE statement LIKE "%FROM route WHERE airline%";
----

Similarly, you can also delete saved plans from `system:prepareds`.
For more information, see xref:n1ql:n1ql-manage/monitoring-n1ql-query.adoc#sys-prepared[Monitor and Manage Prepared Statements].

== View Plan Stability Settings

To get the cluster-wide Plan Stability settings, use the `system:settings` catalog.

[source,sqlpp]
----
SELECT * FROM system:settings;
----

This query returns the current `mode` and `error_policy` values, for example:

[source,json]
----
[
  {
    "settings": {
      "plan_stability": {
        "mode": "ad_hoc",
        "error_policy": "moderate"
      }
    }
  }
]
----

For more information, see xref:n1ql:n1ql-intro/sysinfo.adoc#sys-settings[Monitor Settings].

== Limitations

Consider the following when using Plan Stability: 

* Plan Stability does not support XDCR.
Bucket, scope, collection, and index IDs differ between clusters, so a saved plan from the source cluster is not valid on the target cluster.
* If you drop an object that a saved plan depends on, such as an index, the saved plan becomes invalid.
You must clean up the invalid plan by deleting its prepared statement entry.
Until you delete the entry, the Query Service handles the obsolete plan according to the configured error policy.
For more information about how to delete an entry, see xref:n1ql:n1ql-manage/monitoring-n1ql-query.html#sys-prepared-delete[Delete Prepared Statements].
* Plan Stability does not support transactions that use delta tables.
* Saving and loading plans can increase memory usage and affect query performance.
